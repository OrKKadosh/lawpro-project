# Decisions

Design rationale behind the choices in `PLAN.md` — why, not just what. Written as current-state engineering decisions for a future reviewer, not as a log of how the plan evolved.

Format per entry: **Decision** / **Rationale** / **Trade-off**.

---

## Controlled benchmark and end-to-end pipeline are experimentally separated

**Decision:** The shipping recommendation is computed only from a fixed reference timeline (the controlled benchmark); our own extraction pipeline's output (the end-to-end pipeline) never feeds it.
**Rationale:** If one experiment mixed extraction quality into the summarizer comparison, a bad extraction could look like a bad summarizer, or a lucky extraction could flatter a weak one. Isolating the two makes each answer exactly one question.
**Trade-off:** Two separate result paths and judge-invocation sites instead of one; the end-to-end pipeline's numbers are never directly comparable to the controlled benchmark's leaderboard.

## The supplied Vance reference is treated as a reference, not ground truth

**Decision:** `golden/case-vance.timeline.json` is audited against source OCR/PDF evidence rather than assumed correct.
**Rationale:** The brief describes it as "a reference timeline from our pipeline" — pipeline output, not a hand-curated standard. A direct audit already found a source-unsupported "discrepancy" event and a materially significant omission (`FINDINGS.md`), confirming the reference can be wrong.
**Trade-off:** Requires an audit step before any downstream scoring can be trusted, and requires keeping "provided reference," "source audit," and "our candidate timeline" as three distinct concepts instead of one number — more moving parts, but avoids grading our own extraction against a benchmark we built ourselves.

## Candidate extraction is recall-oriented

**Decision:** The first extraction pass finds and preserves every plausible clinical event; deciding what's important enough for the final attorney timeline happens in a later, separate stage.
**Rationale:** Asking one call to both discover events and judge their relevance means anything it decides is unimportant is gone forever, with no way to audit or recover it. Splitting the stages makes "we missed this" (extraction failure) and "we saw it but dropped it" (salience failure) independently diagnosable.
**Trade-off:** More pipeline stages and more intermediate state than a single-pass extractor.

## Rich intermediate events are preserved before projection to the strict schema

**Decision:** Extraction produces a compact-but-richer internal event representation (provenance, date basis, status, attribution, `clinical_facts`) and only projects to the strict `{date,type,detail,source}` schema at the very end.
**Rationale:** The strict schema is an API contract, not a working representation — it can't hold what's needed to resolve real date traps (explicit vs. billing vs. signing date), performed-vs-planned distinctions, or attribution/certainty, all of which this data set actually requires (`FINDINGS.md`).
**Trade-off:** More schema to design and test than a single-pass extractor; mitigated by keeping `clinical_facts` deliberately compact rather than a full ontology.

## Duplicate clustering and timeline compression are separate problems

**Decision:** `cluster.py` (true duplicates — the same real-world event mentioned in multiple documents) and `salience.py` (distinct-but-repetitive real events, like 40+ individual PT sessions) are different modules with different responsibilities.
**Rationale:** Conflating them risks collapsing genuinely separate events into one, or keeping duplicate mentions as separate final events — different failure modes needing different fixes.
**Trade-off:** Two modules and two test suites instead of one.

## Conflicts are preserved through clustering, resolved only afterward

**Decision:** Clustering groups mentions of the same event and preserves every field value each mention carries; it never picks a winner. Only conflict detection, working on the cluster's full preserved value set, decides what survives.
**Rationale:** A clustering step that also resolves values would silently discard the losing candidates before conflict detection ever saw them — permanent, invisible information loss.
**Trade-off:** Resolution logic lives downstream of clustering rather than inline, adding a pipeline stage.

## Vance and Davis controlled benchmarks are treated symmetrically

**Decision:** Both cases' 8 supplied summaries are used directly as the controlled benchmark — Davis against `input_timeline.json`, Vance against `golden/case-vance.timeline.json` — with no fresh `/v1/summarize` calls required for either.
**Rationale:** Exact input identity is now confirmed for both: Davis by the shipped `input_timeline.json` file itself, Vance by the user's own direct confirmation that its 8 pre-generated summaries were produced from golden (`FINDINGS.md`'s "CONFIRMED FROM USER" section -- re-verified explicitly during the final pre-submission pass, since the fact had previously only been traceable to Claude-authored prose, not a distinct user-provided record). A "controlled" benchmark only requires proven-identical input per tool — once that's established, generating a second, redundant set of fresh calls adds cost without adding rigor.
**Trade-off:** Vance's input-identity confirmation rests on external communication rather than a repo artifact (unlike Davis's `input_timeline.json`), so it's documented as such in `FINDINGS.md` rather than presented as independently data-verified — a minor provenance-quality asymmetry that remains even though the identity claim itself is treated as established for scoring purposes.

## Coverage is measured against a fixed, fact-level material_fact_set

**Decision:** Before any summary is read, a fixed set of material facts (IDs, categories, weights, supporting event IDs) is derived from the exact benchmark timeline and frozen; every tool is scored against the identical set, fact-by-fact.
**Rationale:** Category-level yes/no ("major injuries: yes") hides partial coverage within a category, and raw event-count coverage would penalize a summary for reasonably omitting 40 near-identical PT session mentions.
**Trade-off:** One extra judge call per case to build the fact set, plus a human spot-check, before any tool's output can be scored.

## Cost is reported alongside quality, never blended into a ratio

**Decision:** Cost per summary and projected cost per 1,000 summaries are reported as separate numbers; there is no single "quality ÷ cost" composite.
**Rationale:** A ratio can hide "cheap but unsafe" — a low-cost, low-faithfulness tool could produce an attractive ratio despite being unfit to ship.
**Trade-off:** The final recommendation has to reason about the tradeoff explicitly (prefer cheaper only when quality is effectively tied) rather than read one number off a leaderboard.

## The scoring rubric is frozen before the leaderboard is assembled

**Decision:** Severity-tier definitions, the critical-error gate, and the `material_fact_set` are all fixed before the full A/B/C/D comparison is computed. Known factual discrepancies are used only to sanity-check that the frozen rubric flags them correctly — never to adjust weights afterward.
**Rationale:** Tuning a rubric after seeing which tool wins is how an evaluation quietly becomes a justification for a pre-existing preference rather than a real measurement.
**Trade-off:** If the frozen rubric later proves miscalibrated, fixing it requires an explicit, documented rubric-bug-fix cycle rather than a quiet adjustment — slower, but auditable.

## Chunking config frozen at large (~10 pages + 1-page overlap)

**Decision:** The extraction pipeline chunks documents at ~10 pages per call with 1-page overlap, page-aware, never splitting mid-page.
**Rationale:** The bounded chunking experiment (`results/chunking_experiment.md`, `evalkit/extraction/chunk_experiment.py`) ran small (2-3pp)/medium (~5pp)/large (~10pp) against a frozen local dev set across three representative Vance page windows. Recall and date fidelity were 100% for every config on every window, including catching the billing-vs-operative-date trap in `billing_window` at all three chunk sizes. Large wins clearly on the two metrics that actually differ and are cheap to read (duplicate-candidate rate and cost: lowest duplicate rate, lowest cost at $0.60 vs. $1.19 for small, for identical windows) -- the deciding factors for this freeze.
**Trade-off:** Not extrapolated beyond what was tested — the experiment didn't try chunks larger than ~10pp, so "large wins" is a claim about the three tested sizes, not a claim that bigger is always better. If a real document later produces a genuinely pathological single ~10-page chunk (e.g., one page saturated with distinct events), this config could need revisiting; not observed in the experiment. **Correction, caught by a later adversarial review pass**: the reasoning above originally leaned on "100% recall and date fidelity across every config" as if it were a third data point favoring large, but the one metric in `results/chunking_experiment.md` that could actually catch a large-chunk-specific safety problem -- `unsupported_rate` -- is noisy and non-monotonic across configs (`therapy_window`: 24%→40%→34% small→medium→large; `billing_window`: 80%→76%→81%, roughly flat), by the experiment's own explicit "approximate" caveat and non-exhaustive dev set. It does not favor large, and shouldn't be read as though it does; the decision to freeze large still holds on duplicate-rate + cost alone, which are real and unambiguous, but the write-up shouldn't imply a safety metric that's actually inconclusive was part of what decided it.

## Detail-composition grounding is checked, not just assumed from templating

**Decision:** `project.py` explicitly checks whether an interpreted `clinical_facts` value (e.g. `procedure`, `diagnosis_or_finding`) shares a real, non-numeric word with its cited evidence text before using it in the composed `detail` sentence; if it doesn't, the composer falls back to the raw evidence snippet itself rather than the interpretation.
**Rationale:** The original design assumed templating `detail` from `clinical_facts` was itself sufficient grounding, since the template can't add content beyond those fields. The first real extraction run against case-vance disproved that: for a billing line reading only "Operating Room Services, 27535", extraction populated `clinical_facts.procedure` with a real CPT-code lookup ("open treatment of tibial plateau fracture") and `body_site: "knee"` — accurate general medical knowledge, wrong for this patient, and not stated in the source. The leak happens one stage upstream of where templating operates, so templating alone can't catch it. A naive word-overlap check would also have been fooled here (the phrase and the evidence both literally contain "27535"), so the check specifically requires overlap on a *non-numeric* word — a shared billing code doesn't count as grounding a claim about what that code means.
**Trade-off:** The fallback (raw evidence snippet) reads worse than a fluent interpreted sentence — "Operating Room Services, 27535, 09/04/2023, 1 unit, $28,500.00" instead of a clean clinical description. Accepted: an honest, ungainly sentence beats a fluent, fabricated one. Found and fixed via manual spot-checking of real output, not a systematic scan — `FINDINGS.md` notes this isn't yet verified absent elsewhere in the ~260 combined final events across both cases.

## Severity weights and the critical-error gate, frozen before any controlled-benchmark scoring

**Decision:** Faithfulness severity weights are Critical=5, Major=2, Minor=1. The composite faithfulness score is `1 − Σ(weight of flawed claims) / Σ(weight of all claims)`. On top of that composite, a hard gate: any claim tagged `materiality: critical` with `status` in `{unsupported, contradicted, overclaimed}` sets `ship_eligible: false` for that summary, regardless of the composite score. These numbers are fixed now, before the primary faithfulness+coverage judge runs against the controlled-benchmark summaries.
**Rationale:** The gate, not the weighted composite, is what actually protects against a critical error hiding inside an average — a 5:2:1 ratio still lets enough minor/major claims dilute a composite score for ranking purposes, but the gate makes that irrelevant for the ship/no-ship question specifically, which is the one that matters most. The two known, source-verified calibration examples already found this session (`FINDINGS.md`) anchor this: B-run1's fabricated "September 22" X-ray date and "22-degree" deficit are Major-tier (wrong facts, not a false causal claim or a fabricated procedure) and should pull the composite down without necessarily gating on their own; the Foster/Turner misattribution pattern (a hedged finding turned into unqualified certainty, misattributed across physicians) is exactly the Critical-tier, gate-triggering case this design exists for.
**Trade-off:** These weights and the gate condition are used only to *sanity-check* against the two calibration examples once real judge output exists — not adjusted afterward to make a particular tool rank better or worse (`PLAN.md` §9's freeze rule). If a sanity check fails (the frozen rubric doesn't flag a known issue, or flags something it shouldn't), the fix is a documented rubric correction made before the leaderboard is assembled, logged here as a new decision — never a silent retune after seeing results.

## PDF inspection is escalation-based, not the primary extraction path

**Decision:** Extraction runs over the OCR text by default; the original scanned PDFs are consulted only when OCR looks corrupted, a high-materiality field is ambiguous, two sources conflict, or an outlier value appears.
**Rationale:** Re-reading every page's scanned image by default isn't justified by budget or the exercise's scope, and mirrors a realistic production escalation path rather than an exhaustive one.
**Trade-off:** A small number of OCR errors outside the escalation triggers could go uncaught — a documented, bounded gap rather than an unstated one.

## A populated clinical_facts name field overrides generic text-similarity clustering

**Decision:** In `cluster.py`, two candidates are never merged (in either the exact-date-blocking pass or the near-date pass) if both specify a value for the same `clinical_facts` name-like field (`concept`, `diagnosis_or_finding`, `procedure`, `medication`) and those values share zero significant words — even if the surrounding free-text Jaccard similarity clears the merge threshold.
**Rationale:** Auditing the real conflict output (not just unit tests) found that four genuinely distinct same-day medications in Davis's data (Hydromorphone PCA, Gabapentin, Cefazolin, Oxycodone) were being merged into one cluster, because their administration notes share enough templated boilerplate wording ("mg PO", repeated dosing/route language, the shared date) to clear the 0.25 Jaccard bar on generic text alone — even though each candidate already carried a clean, specific, populated `medication` name that flatly disagreed with the others. The same failure mode explained a second bogus merge ("industrial machinery entrapment" merged with "ED physician history and physical" — an injury-mechanism fact and a note-type label, zero shared words). This was previously showing up downstream as an unresolvable field-level "conflict" that `conflict.py` correctly refused to auto-resolve — the conflict-resolution rule wasn't broken, but it was being handed garbage: two-plus genuinely different real events dressed up as one event with disagreeing fields.
**Trade-off:** A specific named fact now always wins over generic text similarity, which could in principle keep apart two mentions of the same event if one source names it more specifically than the other (verified NOT to happen for the "same medication reworded" case, which still merges correctly since real synonyms/abbreviations of the same drug share at least one significant word) — but a case where two sources both name the *same* real-world fact with completely non-overlapping vocabulary (e.g. a brand name vs. an unrelated-sounding generic name, sharing zero words) would now stay unmerged. Judged an acceptable trade since under-merging leaves both mentions independently auditable in the final timeline, while over-merging silently discarded real distinct clinical facts as "conflicting" values on one fake event. Verified on real cached data (free re-run, no new API cost): case-vance conflicts 128→58, clusters 235→279, final timeline events 145→160; case-davis conflicts 63→13, clusters 135→161, final timeline events 114→146; 0 schema-validation problems on both, before and after.

## Two attempts to fix the "clearly distinct" name-field check were tried and BOTH reverted -- it ships unchanged

**Decision:** `cluster.py`'s `facts_clearly_distinct()` and `NAME_FIELDS` ship exactly as they were before this investigation (`NAME_FIELDS = (concept, diagnosis_or_finding, procedure, medication)`; checks every populated field pair, blocks a merge if ANY pair disagrees, order-independent by construction since only disagreement causes an early return).
**Rationale:** A fresh-context `code-reviewer` pass traced FINDINGS.md's Harrison/X-ray fabrication (case-vance) to this function: `concept` disagrees between the two mentions ("imaging study" vs. "X-ray cervical spine (prior)", no shared words), which alone is enough to block the merge under "any field disagrees -> distinct" -- regardless of the fact that `procedure` ("X-ray cervical spine, three-view series" vs. "X-ray") agrees. Two fixes were tried in response, both tested for real against the full cached candidate set (not just a unit-test fixture), and both found unsafe:
1. **Stop at the single most-specific field both candidates populate, in priority order, instead of scanning every field.** This does unblock Harrison/Finch in isolation. But a SECOND fresh-context `code-reviewer` pass, specifically re-reviewing the first fix, found it silently dropped a `materiality="high"` billing event (an Anesthesia line, CPT 01402) from case-vance's real final timeline: two genuinely different billed procedures' `procedure` fields shared only the boilerplate token "CPT", registered as "agreeing" at that now-highest-priority field, and the function stopped there -- never reaching the genuinely-disagreeing fields the original check-everything logic would have caught. ~16 case-vance and 4 case-davis real cluster groups were affected, several as genuine over-merges. The first hand-check of "every changed event" (done by the same session that made the fix, before the second review) missed this -- it takes systematically diffing cluster membership against the pre-fix code and tracing every changed cluster to the projected timeline to catch, not spot-checking a handful of examples.
2. **Make field agreement actively force a merge**, tried when fix #1 alone still didn't merge Harrison/Finch (their Jaccard, ~0.12-0.18, never clears `SIMILARITY_THRESHOLD=0.25`). Collapsed case-vance's final timeline from 202 to 137 events for the same boilerplate-token reason, at corpus scale.

**Trade-off:** Both reverted; re-running the deterministic pipeline on both cases' cached candidates after reverting confirms an EXACT match to the originally-frozen files (case-vance 315 clusters/202 final events, case-davis 170 clusters/140 final events, both unchanged, 0 validation problems) -- so no reconciliation of `runs/candidate_timelines/*.json`/`results/timeline_eval/*.json`/`results/pipeline_demo_*.json` was needed. The Harrison/X-ray fabrication remains genuinely unresolved. A real fix needs boilerplate/generic tokens (bare CPT-code prefixes, category words like "urine drug screen") excluded from the word-overlap comparison, likely combined with dropping the unreliable, loosely-worded `concept` field from consideration entirely -- a larger, dedicated-dev-set-verified redesign (mirroring the chunking/prompt-experiment methodology already used elsewhere in this project) than remaining time/budget supported doing safely in this session. Worth recording plainly: this is the second time in this project that a plausible-looking, unit-tested fix in this exact function turned out unsafe only once verified against the FULL real dataset rather than a handful of examples -- a concrete argument for why "verify claims for real" (this project's standing discipline, `ERRORS.md`) applies especially hard to clustering/dedup logic, where a change's blast radius is corpus-wide and not obvious from a small diff.

Also worth naming plainly, surfaced by the same review passes: the medication-splitting fix above (`A populated clinical_facts name field overrides generic text-similarity clustering`) has a known, still-open edge case -- two sources naming the SAME real event with zero shared vocabulary (e.g. a brand name vs. an unrelated-sounding generic name) would wrongly stay unmerged, same as documented in that entry's trade-off. Verified NOT to happen for either case tested, but not proven impossible for a case with different naming conventions -- one more concrete instance of this project's general "no held-out case to validate against overfitting" limitation, below.

## Extraction prompt iteration: a "reinforced" variant is frozen, replacing the original

**Decision:** `EXTRACTION_SYSTEM_PROMPT` in `candidates.py` is replaced with the "reinforced" variant developed in `prompt_experiment.py` — same base instructions, plus two explicit rules: (1) never populate `clinical_facts` using outside medical-coding knowledge when a source line gives only a code with no clinical narrative; (2) when a note's signer differs from a physician specifically named as the one consulting/ordering/performing a described action, attribute that action to the named actor, not the signer.
**Rationale:** This closes a real methodological gap: chunk size was tuned against a frozen dev set (`results/chunking_experiment.md`), but the extraction prompt itself had only ever been bug-fixed reactively, never systematically compared against an alternative. Ran a bounded experiment mirroring the same methodology — frozen dev set (the 3 existing chunking-experiment windows plus one new window, `ems_window`, built from real OCR text read directly from the source, not guessed) — and added two trap checks tied to the two real fabrication/misattribution bugs found in step 5. Result: recall (100%), date fidelity (100%), and duplicate rate were statistically unchanged between variants (no regression from the added instructions) — full comparison table in `results/prompt_experiment.md`. The grounding trap was cleanly fixed (`baseline: VIOLATED` → `reinforced: clean`) on the real CPT-27535 line, upstream of the existing `project.py` grounding-check fix (defense in depth, not redundant — a bad value never even enters `clinical_facts` now, rather than being caught and stripped later).
**Trade-off / methodological correction made honestly rather than glossed over**: the attribution trap's *first* result (both variants "correct") was a false positive — the `ems_window` test slice (pages 1-5) was narrower than the full 9-page document the real production bug actually occurred on, and was too easy for either prompt to pass. Caught this before trusting the result: re-ran both prompts against the *exact* full 9-page chunk that produced the real bug (2 extra calls, $0.2651). Baseline reproduced a wrong attribution there too (`"ED physician"`, a vague non-answer — not even the specific wrong name from the original production run, confirming the failure is a general "defaults away from the named actor" pattern, not one specific fluke); reinforced correctly named `"Dr. Myrtle Turner"`. This is the actually-trustworthy confirmation the fix works, and it's the one the freeze decision is based on — not the original narrow-window result. Total prompt-experiment cost: $1.448 (12 calls) + $0.2651 (2 verification calls) = $1.7131.

## salience.py compression grouping: a name-aware fix, corrected twice after real-data testing

**Decision:** `select_material_timeline_events`'s routine-event compression no longer groups purely by `(type, provider)`. Within that bucket, events are split further: any event with a populated `medication` value is grouped by an EXACT normalized key on that field; everything else (no `medication` value) is grouped by fuzzy word-overlap across `concept`/`procedure`/`diagnosis_or_finding` pooled together (`SOFT_NAME_FIELDS`), same as the original design's spirit.
**Rationale:** After the fresh full-extraction re-run (frozen prompt + clustering fix), spot-checking real Davis output found the compression stage still silently discarding real distinct medications: 36 medication-type events shared `provider: None`, so the old `(type, provider)` grouping put every drug given during a hospital stay into ONE bucket and compressed it to essentially first+last, regardless of which drug. This is the same class of bug as the clustering fix above, one stage downstream.
**Trade-off / two false starts, corrected honestly rather than shipped on the first pass that looked right:**
1. First attempt reused `cluster.py`'s per-field "clearly distinct" check directly inside a single fuzzy union-find pass over the whole bucket. Real-data testing caught a genuine flaw before it was trusted: a compound "transitioned to Oxycodone and Gabapentin" candidate shares one word with pure-Oxycodone events and a different word with pure-Gabapentin events; union-find's transitive closure chained the two drugs (and, via further weak links, several more) into one 26-member group — even though any direct pair of those drugs would correctly evaluate as distinct. A pairwise "not distinct" veto is not a transitive relation, and union-find doesn't respect that; this is a structurally different failure from the clustering fix, not the same bug recurring.
2. Second attempt fixed the transitivity problem (exact-key grouping for a `HARD_NAME_FIELDS` tier, no union-find bridging possible through a dict key) but initially scoped that hard tier to `medication`/`procedure`/`diagnosis_or_finding` together. Real-data testing caught a second flaw: real repetitive PT-visit candidates commonly populate `procedure` with descriptive text that varies phrase-to-phrase ("physical therapy" vs "ambulation with PT"), so exact-keying on it fragmented real PT courses into near-singletons instead of compressing them (a correctness regression in the opposite direction — under-compression instead of over-merging).
3. Final design: `HARD_NAME_FIELDS = ("medication",)` only — the one field confirmed to be short, specific, and consistently worded across real repeated mentions. Everything else pools into the fuzzy tier, restoring correct PT-course compression while keeping medications exactly separated.

Verified against real data at each step (free, deterministic re-runs on cached candidates, no new API cost) before moving on: final medication sub-group sizes went 26 (broken) → max 10 (correct, per-drug), and therapy sub-group sizes went from full per-provider courses (63, 58 — correct) → fragmented to near-singletons (broken, first fix) → back to full per-provider courses (63, 58 — correct, final fix). Two new regression tests added (`test_salience_compression_does_not_merge_distinct_routine_medications`, `test_salience_compression_ignores_a_compound_mention_as_a_bridge`), 17/17 tests passing.

## Severity-tiered extraction-vs-golden scoring, reusing the faithfulness-scorer's vocabulary

**Decision:** `evalkit/reference/compare.py`'s `score_extraction_against_golden()` replaces the old flat `reference_agreement` recall number with four tiers, using the exact same `critical=5, major=2, minor=1` weights already frozen for summary faithfulness scoring (`evalkit/scoring.py`'s `SEVERITY_WEIGHTS`), not a new invented scale:
- **missing** (major) — a corrected-golden fact we never found.
- **matched_contradicted** (critical) — a candidate event aligned to a golden event by date+type that a judge call confirms describes the *same real event* but disagrees on a specific detail within it.
- **extra_grounded** (minor) — a candidate event with no golden match, but independently confirmed against real OCR by the audit that's already run for `source_grounded_precision` — real information, just not in golden.
- **extra_ungrounded** (critical) — a candidate event with no golden match and no independent source support — the one tier that would actually catch a fabrication.
- **extra_unaudited** — outside the risk-based audit's coverage (a routine event not in the deterministic sample); reported in the counts but deliberately excluded from the composite (severity `None`) rather than guessed at.

Composite: `1 − Σ(weight of flawed items) / Σ(weight of scored items)`, identical formula shape to `score_faithfulness`. `has_confirmed_fabrication` is a boolean flag (not a hard ship/no-ship gate — nothing is being "shipped" here, this is a self-diagnostic, not the tool-selection decision) that's `true` the instant any `extra_ungrounded` item exists.
**Rationale:** Directly answers the user's own explicit ordering request — "an extra correct fact is not as bad as a missing fact, which is not as bad as a wrong fact" — as a literal weight ordering (1 < 2 < 5), verified with a unit test (`test_extra_grounded_fact_is_penalized_less_than_missing_or_contradicted`) rather than just asserted. Reusing `evalkit/scoring.py`'s exact vocabulary and weights, instead of inventing a second severity system, is a direct response to the "over-engineered, too many new concepts" complaint — anyone who already understands the faithfulness gate already understands this one too.

**A real design flaw found and fixed before this was ever reported as a finding, not after:** the first version only sent *weak* matches (Jaccard below a threshold) to an agree/contradict check, on the assumption that a low text-overlap score meant "probably the same event, but worth double-checking for a factual disagreement." Running it for real and directly inspecting all 6 of Vance's flagged "contradictions" before writing them anywhere showed every single one was actually a **bad alignment** — two genuinely unrelated events (an Acetaminophen entry vs. an unrelated IV-antibiotics order; an alcohol-intoxication finding vs. an unrelated left-knee-contusion finding) force-paired by the greedy matcher because nothing better existed in the date/type window, not the same event described inconsistently. The judge correctly recognized they didn't match; the scoring code wrongly turned "these are different things" into "critical fabrication." Checking the *other* direction confirmed the threshold itself was unreliable too: several legitimately-correct matches (a CPT billing-code line vs. its own visit's narrative description) scored as low as 0.13, well below where the flawed logic drew its "confident" line.

Fixed by giving the judge a third option (`different_events`, alongside `same_event_agrees`/`same_event_contradicts`) and checking **every** date+type-aligned pair, not just the weak ones, since score turned out not to predict which pairs actually needed checking. A `different_events` verdict reclassifies the pair as a missed reference fact plus a separately-tiered extra candidate fact — never a contradiction. A regression test (`test_score_extraction_against_golden_reclassifies_different_events_instead_of_contradicting`) encodes the exact real scenario that broke the first version.
**Trade-off — budget discipline, checked before spending:** the alignment (`align_events`) and the source-grounding signal (`candidate_audit.source_support_by_index`) are both already computed elsewhere at no extra cost; the only new spend is one batched call per case covering every matched pair — still one call regardless of count, so checking all of them instead of a "weak" subset cost nothing extra in practice ($0.02-0.03/case). The scoring math itself (`_score_items`) is a pure function, unit-tested with hand-built cases before any real money was spent, and the full wiring was dry-run with mocked API calls first — but the *false-positive-proneness of the weak-match heuristic itself* was only found by reading real flagged output before trusting it, not by any test written in advance. Worth stating plainly: "test before spending" catches wiring bugs; it doesn't substitute for reading what a new heuristic actually produces on real data before reporting it as a finding.

## align_events: undated and cross-type reference events can match too, on strong content overlap

**Decision:** `align_events` no longer hard-requires exact date proximity or exact type equality to consider two events a match. Two relaxations, each independently sufficient (not stacked as an AND when both apply): an undated reference event can match a dated candidate on content alone if the Jaccard score clears `UNDATED_MIN_SCORE=0.2`; a type-mismatched pair can match if the score clears `CROSS_TYPE_MIN_SCORE=0.3`. When both conditions apply to the same pair, the *lower* of the two thresholds governs, not both stacked together.
**Rationale:** The first real run of the golden-pivot scoring produced a composite score (0.582) that looked alarming on its face. Investigating directly, rather than either dismissing the concern or accepting the number at face value, found the true composite was legitimate but the underlying "missing" count was significantly inflated by two structural bugs, not real extraction gaps:
1. Golden's two *most material facts in the entire case* — the Foster/Turner pre-existing-condition findings, the exact facts behind three of Vance's four summarizer tools failing the faithfulness gate — are both **undated** in golden. The old date-tolerance check computed 9999 days apart whenever either side lacked a date, so these two facts could never match anything, by construction, regardless of content. Confirmed the same real content exists in our candidate timeline, correctly dated, in more detail than golden.
2. Several real facts (the Turner ORIF-consult event, the alcohol/intoxication event) are classified under a different `type` by our extraction than by golden for the exact same real event (e.g. golden's "encounter" vs. our "procedure" for the same consult) — the old strict type-equality requirement blocked these regardless of content overlap.
Both were confirmed by direct inspection of the real flagged "missing" events against the real candidate timeline before writing any fix, the same discipline already applied to the `different_events` fix above.
**A bug found while fixing this one, same session:** the first version of this fix required a pair to clear *both* relaxation thresholds when both applied (undated AND type-mismatched at once), which is what one of the two Foster/Turner facts actually is. That wrongly excluded a real, manually-verified match that cleared the easier undated bar but not the stricter cross-type bar on its own. Fixed by taking the lower of the two applicable thresholds instead of requiring both — each relaxation is independently sufficient justification, not a penalty to be compounded. A regression test encodes this exact combined case.
**Trade-off:** Both thresholds were set by direct inspection of the specific real cases that motivated them (there are only 2 undated events in the whole Vance dataset, both individually read before picking a number), not derived from a larger, more statistically-grounded calibration set — a known limitation consistent with the project's broader acknowledged overfitting risk (`DECISIONS.md`: "no held-out case to validate against overfitting"). Regression tests guard against the two relaxations becoming a blanket "anything sort of matches" pass (`test_align_events_rejects_undated_match_with_weak_content_overlap`, `test_align_events_rejects_cross_type_match_with_weak_content_overlap`).

## Audit "partial" support with a flagged issue must not count as grounded

**Decision:** `AuditReport` now tracks `issue_by_index` alongside `source_support_by_index`. Both `AuditReport.to_dict()`'s `source_grounded_precision` and `compare.py`'s `_tier_extra` now treat a candidate event as genuinely grounded only when support is `"yes"`, or `"partial"` with no flagged issue — a flagged issue (`wrong_attribution`, `contradicted`, `unsupported`, `wrong_date`) means something is confirmed wrong regardless of the yes/partial/no support value.
**Rationale:** Checking why `has_confirmed_fabrication` unexpectedly flipped to `false` after the alignment fix (rather than assuming the fabrication had somehow resolved itself), the real audit response for the Harrison/X-ray misattribution showed the judge had correctly flagged it: `source_supports: "partial"`, `issue: "wrong_attribution"`, confidence 0.85 — matching the manual source verification exactly. The scoring code only ever checked `support in ("yes", "partial")` and never looked at `issue` at all, so a correctly-flagged real problem was silently absorbed into the "grounded, minor" tier. This also affects the already-reported `source_grounded_precision` headline number (which counted "partial" as supported unconditionally) — not just the new extraction-scoring tiers, so it's fixed at the source in `audit.py` rather than patched around downstream.
**Trade-off:** None — this is a straightforward correctness fix; the "partial + no issue" case (genuinely incomplete but not wrong) is still counted as supported, so an honest hedge doesn't get penalized the same as a confirmed error.

## Human-readable conflict review is a presentation layer, not a pipeline change

**Decision:** `evalkit/report_readable.py` renders `results/conflict_review_<case>.md` — a plain-English paragraph per cluster that had a real disagreement or HITL flag, generated by re-running the already-existing deterministic pipeline stages on cached candidates (free — pure code, no LLM call) and formatting their output, rather than by asking a model to narrate.
**Rationale:** Direct response to a concrete, specific complaint: reading `runs/candidate_timelines/case-vance.json` directly wasn't enough to tell that cluster `cl003` was one real vitals check documented independently by three people with no way to credit a single provider. The underlying pipeline stages (clustering, conflict detection, canonicalization, salience) were kept exactly as-is per the user's explicit choice — the richness there is what's catching real bugs (the billing-date trap, the medication-compression bug); the actual problem was that the only way to see it was raw JSON with field names like `authority_rank`. Real output: 41 of case-vance's 315 clusters had something worth flagging — a genuinely reviewable number, not an overwhelming one.
**Trade-off:** One more module and one more `results/` artifact to keep in sync with the pipeline; justified since it directly targets the "too many fields, not clear enough" complaint without touching the fields or the pipeline itself.

## Acknowledged limitation: no held-out case to validate against overfitting

**Decision:** No new held-out third case is being constructed to test generalization. This is documented as a known, undeleted limitation of every fix made against real Vance/Davis output (clustering, salience, the reinforced extraction prompt) rather than something the write-up should imply is more validated than it is.
**Rationale:** With only two test cases, and both of them read repeatedly while debugging, there is no way to actually measure whether a fix generalizes versus merely matching what was observed in these two records. The mitigation actually taken — keeping every fix framed as a general principle ("a populated specific-name field beats generic text overlap on shared boilerplate," not "if medication contains Hydromorphone") rather than a case-specific rule — reduces the risk but does not prove it away, and the write-up should say so plainly rather than let a clean test-suite pass imply broader validation than two cases can support.
**Trade-off:** None avoided by declining to build a third case — this is a real, acknowledged gap in the evidence, not a trade-off with a compensating benefit.
